Every line of code we write today in the bootcamp eventually needs to reach real users. That journey from "it works on my machine" to "my users can reach it" is what we cover today. Let's be specific about what changes.

Block 2 — Docker: Containerise the Agent

40 minutes · File: Dockerfile

What Is a Container?

A container packages your application with everything it needs — Python version, libraries, system settings — into a single self-contained unit. Build it once, and it runs identically on your laptop, a colleague's machine, or an AWS server in Singapore.

Think of it like shipping a product in a box. The box (container) contains exactly what's needed. The courier (cloud provider) doesn't need to know what's inside — they just deliver the box.

Walking Through Our Dockerfile

Open Dockerfile in the project root. Every line has a deliberate reason.

Dockerfile
# syntax=docker/dockerfile:1 FROM python:3.11.9-slim-bookworm AS base

Why slim-bookworm?

The "slim" variant strips out documentation and unused tools — smaller attack surface, faster image pulls. Smaller images deploy faster and cost less to store in ECR.

Dockerfile — ENV block
ENV PYTHONDONTWRITEBYTECODE=1 \ PYTHONUNBUFFERED=1 \ PIP_NO_CACHE_DIR=1 \ PIP_DISABLE_PIP_VERSION_CHECK=1
VariableWhy It Matters
PYTHONDONTWRITEBYTECODE=1No .pyc files → smaller image
PYTHONUNBUFFERED=1Log output goes to stdout immediately — critical for cloud log streams
PIP_NO_CACHE_DIR=1Don't cache pip downloads inside the image → smaller image

🔒 Non-Root User — Non-Negotiable Security

Dockerfile — Security
RUN addgroup --system --gid 10001 appgroup \ && adduser --system --uid 10001 --ingroup appgroup app USER 10001

⚠️ Never run as root

If someone exploits your app, they get a restricted system user — not root access to the whole machine. This is non-negotiable in enterprise deployments. Our K8s manifest enforces this too: runAsNonRoot: true, runAsUser: 10001.

🚀 Layer Caching — The Most Important Docker Performance Trick

Notice the order in the Dockerfile:

Dockerfile — Layer ordering
COPY requirements.txt . # ← copied FIRST RUN pip install -r requirements.txt COPY app ./app # ← application code copied AFTER
❌ Wrong Order

Copy all files first, then pip install. Every single code change re-installs ALL packages. A 3-minute install on every deploy.

✅ Our Order

requirements.txt first. Docker caches the pip install layer. Code change? Only the app layer rebuilds. Deploy is seconds faster.

🧪 Build and Run Locally

Terminal
# Build the image docker build -t support-ops-agent:local . # Run it — inject the API key as environment variable docker run --rm -p 8000:8000 \ -e OPENAI_API_KEY="$OPENAI_API_KEY" \ -e SECRETS_SOURCE=env \ support-ops-agent:local # Test it curl -s http://localhost:8000/health # → {"status":"ok"}

Best Practices Checklist

  • ✓ Pin exact base image tag (python:3.11.9-slim-bookworm) — reproducible builds
  • ✓ Non-root user (UID 10001) — security
  • ✓ Copy requirements.txt before app code — layer caching
  • ✓ PYTHONUNBUFFERED=1 — logs appear immediately in cloud
  • ✓ EXPOSE 8000 — documents intent, required by orchestrators
  • ✓ exec-form CMD: ["uvicorn", ...] — signal handling for graceful shutdown
  • ✗ Never embed secrets in Dockerfile — they get baked into image layers forever
  • ✗ Never use :latest tag in production — not traceable, not reproducible
🔑 Key Insight
A good Dockerfile is not just build instructions — it is documentation of your deployment contract.

💡 Why git SHA as the image tag?

Using the commit SHA (not "latest") means every deployed image is 100% traceable. You can always answer: what exact code is running in production right now? — and roll back with confidence.

🔑 Key Insight
Never deploy "latest" in production. A git SHA tag is your audit trail.

Block 4 — Secrets & Environment Variables

30 minutes · Files: app/core/config.py & app/core/secrets.py

⛔ The Secrets Problem

Your agent needs an OpenAI API key. In development you put it in a .env file. In production that approach fails — .env files do not belong in Docker images or git repos. They do not rotate, audit, or centralise. A leaked key in a Docker image has cost teams thousands of dollars in hours.

Our Solution — A Pluggable Secrets Provider

The codebase uses an abstraction: a SecretsProvider that switches automatically based on environment. Open app/core/secrets.py:

app/core/secrets.py — the abstraction
class SecretsProvider(ABC): @abstractmethod def get_openai_api_key(self) -> str: ... class EnvSecretsProvider(SecretsProvider): # reads OPENAI_API_KEY from the process environment def get_openai_api_key(self) -> str: return os.environ["OPENAI_API_KEY"] class AwsSecretsManagerProvider(SecretsProvider): # calls AWS Secrets Manager, parses JSON, caches the result def get_openai_api_key(self) -> str: secret = self._client.get_secret_value(SecretId=self._secret_name) return json.loads(secret["SecretString"])["OPENAI_API_KEY"]

🏛️ This is the Strategy Pattern

The app only calls get_openai_api_key(). It does not care whether the key comes from an env var or AWS. Swapping providers requires zero changes to business logic.

How the Provider Is Chosen — config.py

Open app/core/config.py. The secrets_source field defaults to "auto":

app/core/config.py — auto-switching logic
@property def resolved_secrets_source(self) -> Literal["env", "aws_secrets_manager"]: if self.secrets_source != "auto": return self.secrets_source # auto mode: production/staging → AWS Secrets Manager, else → env if self.environment.lower() in {"production", "staging"}: return "aws_secrets_manager" return "env"

The Secrets Hierarchy — Where Each Value Lives

❌ NEVER
Hardcoded in code or Dockerfile
e.g. api_key = "sk-abc123" — baked into image layers, visible in git history forever
DEV ONLY
.env file / local environment variable
Fine on your laptop. Never commit. Never inside a container image.
CONFIG
Kubernetes ConfigMap / environment variables
For non-sensitive config: ENVIRONMENT, LOG_LEVEL, OPENAI_MODEL, ENABLE_CLOUDWATCH_LOGGING
✅ PRODUCTION
AWS Secrets Manager
For OPENAI_API_KEY and any credential. Fetched at runtime, audited, rotatable, never in YAML.

Setting Up AWS Secrets Manager

Terminal — one-time setup per environment
# 1. Create the secret aws secretsmanager create-secret \ --name "support-ops-agent/openai" \ --secret-string '{"OPENAI_API_KEY": "sk-..."}' # 2. Grant EKS pod permission via IAM role (IRSA) # secretsmanager:GetSecretValue on the secret ARN # 3. Set environment or secrets_source flag # ENVIRONMENT=production → auto picks AWS Secrets Manager
🔑 Golden Rule of Secrets
If a value would cause damage if leaked, it belongs in Secrets Manager. If it is just configuration, a ConfigMap is fine. Never put secrets in YAML manifests, Dockerfiles, or git.

Block 5 — CI/CD Pipelines for AI Agents

30 minutes · File: .github/workflows/deploy.yml

What Is CI/CD and Why Do AI Teams Need It?

CI/CD = Continuous Integration / Continuous Deployment. Every time you push code, an automated pipeline tests it, packages it, and deploys it — without anyone running commands manually.

For AI agents this matters even more: your agent's behaviour changes every time you adjust a prompt, a tool, or a graph node. Without CI/CD, you can never be sure what is actually running in production.

📐 The CI/CD Mental Model

git push → tests run → if green → new version goes live → rollback is just another git push

Our Pipeline — Two Jobs

Open .github/workflows/deploy.yml. Triggered on every push to main.

✅ Job 1: test
Runs on every push to main
StepWhat It Does
1actions/checkout@v4 — check out the code
2Set up Python 3.11 with pip caching
3pip install -r requirements.txt
4pytest with SECRETS_SOURCE=env and a dummy API key

Why a dummy API key in CI?

Tests mock the LLM — they never call the real OpenAI. So OPENAI_API_KEY=sk-test-ci is valid. Real secrets never touch the CI runner.

🚀 Job 2: build-push-deploy
Only runs if Job 1 (test) passes — needs: test
StepWhat It Does
1Configure AWS credentials from GitHub secrets
2Log in to Amazon ECR
3Build Docker image tagged with ${{ github.sha }}
4Push image to ECR
5Install kubectl, update kubeconfig for EKS cluster
6Inject real image URI into deployment.yaml (sed replace)
7kubectl apply all Kubernetes manifests
8kubectl rollout status — wait for completion

GitHub Secrets Required

.github/workflows/deploy.yml — secrets used
AWS_ACCESS_KEY_ID # AWS credentials for the CI runner AWS_SECRET_ACCESS_KEY # (prefer OIDC for production — see tip below) AWS_REGION # e.g. us-east-1 AWS_ACCOUNT_ID # your 12-digit AWS account number ECR_REPOSITORY # name of the ECR repo EKS_CLUSTER_NAME # name of your EKS cluster K8S_NAMESPACE # support-ops-agent

💡 OIDC Tip (production upgrade)

The workflow has id-token: write permission — this is the hook for switching to GitHub OIDC later. OIDC eliminates static AWS keys entirely: GitHub proves its identity to AWS directly. No long-lived credentials.

What Happens If a Test Fails?

build-push-deploy has needs: test. If tests fail, deployment never starts. Your broken code cannot reach production. This is the CI/CD safety net.

🔑 Key Insight
CI/CD is not a DevOps luxury — it is the mechanism that lets you move fast without breaking things. Every serious AI team ships with a pipeline.

Block 6 — Kubernetes Manifests & Infrastructure as Code

20 minutes · Folder: deployment/k8s/

What Is Infrastructure as Code?

IaC means your infrastructure — deployments, networking, scaling — is described in files that live in git, just like your app code. Instead of clicking through cloud consoles, you write YAML and let tools apply it. Anyone with cluster access can deploy with one command.

The Five Files in deployment/k8s/

FileWhat It Does
namespace.yamlCreates an isolated namespace — keeps our workload separate from others on the cluster
serviceaccount.yamlIdentity for the pods — annotated with IAM role for Secrets Manager access (IRSA)
configmap.yamlNon-sensitive env vars: ENVIRONMENT, LOG_LEVEL, OPENAI_MODEL, ENABLE_CLOUDWATCH_LOGGING
service.yamlExposes the deployment inside the cluster (ClusterIP) so traffic can reach our pods
deployment.yamlThe main workload spec — replicas, image, probes, resources, rolling update strategy

Walking Through deployment.yaml

Replicas & Rolling Update

deployment/k8s/deployment.yaml — rolling update
spec: replicas: 2 # two pods for high availability strategy: type: RollingUpdate rollingUpdate: maxUnavailable: 0 # never take a pod down before a new one is ready maxSurge: 1 # spin up one extra pod during the update

🔄 Zero-Downtime Deployments

maxUnavailable: 0 means Kubernetes brings up the new pod first, checks it is healthy (readiness probe), then terminates the old one. Users never see an outage during a deploy.

Resource Requests & Limits

deployment/k8s/deployment.yaml — resources
resources: requests: cpu: "250m" # 0.25 of a CPU core guaranteed for scheduling memory: "512Mi" # 512 MB guaranteed limits: cpu: "1000m" # max 1 full CPU core memory: "1Gi" # max 1 GB — OOM kill if exceeded

Why set both requests and limits?

Requests are what Kubernetes uses to schedule pods onto nodes. Limits prevent a runaway LLM call from eating all memory on the node. Always set both for AI workloads.

Liveness & Readiness Probes

deployment/k8s/deployment.yaml — probes
livenessProbe: httpGet: path: /health # GET /health must return 200 initialDelaySeconds: 15 periodSeconds: 20 readinessProbe: httpGet: path: /ready # GET /ready must return 200 initialDelaySeconds: 5 periodSeconds: 10 failureThreshold: 6 # 6 failures = 60s before marked not-ready
ProbeEndpointWhat It ChecksOn Failure
LivenessGET /healthIs the process alive?Kubernetes restarts the pod
ReadinessGET /readyAre config + secrets loadable?No traffic sent to this pod

The ConfigMap Pattern

deployment/k8s/deployment.yaml — envFrom
envFrom: - configMapRef: name: support-ops-agent-config

All keys in the ConfigMap become environment variables in the container. Sensitive values (OPENAI_API_KEY) are fetched at runtime from Secrets Manager — they never appear in the ConfigMap.

🔑 Key Insight
Kubernetes manifests are your system's contract. They describe exactly what should run, where, how many replicas, with what resources — and git records every change to that contract.
📣 DEMO: Open deployment.yaml and configmap.yaml side by side. Ask: "Why does the ConfigMap have OPENAI_MODEL but not OPENAI_API_KEY?" — This forces learners to connect Block 4 and Block 6 together.

Block 7 — End-to-End Walkthrough

25 minutes · git push → live endpoint

The Complete Deployment Journey

Trace a single code change all the way to a live endpoint. This is the journey every commit takes once your pipeline is in place.

1
Write code — add a node to LangGraph, fix a bug, improve a prompt
2
Commit & push to main — git commit -m "improve classify node" && git push
3
GitHub Actions triggers automatically — no manual steps
4
Job 1 (test) — pytest runs; the commit must earn its deploy
5
Job 2 (build-push-deploy) — Docker image built, tagged with commit SHA, pushed to ECR
6
kubectl apply — new Kubernetes manifests sent to EKS
7
EKS rolling update — new pods come up, /ready probe passes, old pods terminate
8
kubectl rollout status confirms success — pipeline exits green
9
Your agent is live. Call /agent/respond and see the new behaviour.

Deployment Checklist & Quick Reference

Use this before every production deploy

✅ Pre-Deploy Checklist

  • ✓ Dockerfile uses non-root user (UID 10001) and slim base image
  • ✓ requirements.txt copied before application code (layer caching)
  • ✓ PYTHONUNBUFFERED=1 set for immediate log streaming
  • ✓ OPENAI_API_KEY in AWS Secrets Manager — NOT in code, YAML, or ConfigMap
  • ✓ ConfigMap holds only non-sensitive environment variables
  • ✓ Docker image tagged with git SHA, not "latest"
  • ✓ Kubernetes deployment has both liveness and readiness probes
  • ✓ Resource requests AND limits set on every container
  • ✓ RollingUpdate strategy with maxUnavailable: 0 for zero-downtime
  • ✓ GitHub Actions pipeline: tests must pass before deploy runs
  • ✓ kubectl rollout status confirms successful rollout
  • ✓ POST /ready returns 200 after deploy
